# 解析检查规则（RULES）

`meow_lint.py` 的判定依据。每条规则都对应一个能踩的坑。

## 用法

```bash
# 检查
python tools/meow_lint.py lint 解析.txt

# 检查 + 转成结构化数据
python tools/meow_lint.py build 解析.txt --out data/
```

退出码：有 ERROR 返回 1，否则 0。可直接接 CI。

---

## 规则表

| 编号 | 级别 | 判什么 | 为什么 |
|---|---|---|---|
| **R0** | — | 能否解析出段落块 | 标题必须是 `**第N段解析**` 或 `**第N-M段解析**` |
| **R1** | ERROR | 每块必须有【灵感】和【全局作用】 | 这两栏是骨架；缺了整块就只剩零散判断 |
| **R2** | ERROR | 【缺陷】里必须有修法 | 只写"这里不好"不写"应该怎么改"，等于没复盘 |
| **R3** | WARN | 有【缺陷】就该有反例 | 缺陷是"本来能更好"，反例是"换成别的会怎样"，两者互为证据 |
| **R4** | WARN | 反例要成对 | 只有"删了会怎样"或只有"写歪了会怎样"，都是单向的，约束力弱 |
| **R5** | WARN | 不能用通用修辞名 | 承上启下、对比衬托、推动剧情……这些只是给现象起名字，不给判据 |
| **R6** | ERROR | 术语必须一致 | 碎片式→碎片化、情绪铺垫→氛围铺垫、首位呼应→首尾呼应、喻示→预示 |
| **R7** | INFO | markdown 符号残留 | txt 本体允许；发知乎前要去符号 |
| **R8** | ERROR | 交叉引用不越界 | 写"详见深度探索5"但全文只有 3 节 |

---

## 几条设计说明

**R5 为什么最重要。**

通用修辞名是最容易写的，也是最没用的。"这一段用了对比衬托"——读者学不到任何东西，因为对比什么、衬托谁、到什么程度，全没说。

**判据是：这个词你能不能说清"怎么做、什么时候失效"。** 说得出是机制，说不出是命名。

跑一遍能看到差距：第一版出现 22 次通用修辞名，第二版 0 次。

**R6 会跳过"自我修正"句。**

比如这一句：

> 作者回看时发现"情绪铺垫"这个说法有误，因为情绪的变化是铺垫带来的结果，故改为"氛围铺垫"

它引用了旧词，但那是**证据**，不是错误。检查器会跳过含"改为/有误/说错/更正"的句子。

**R2 的局限。**

五步里"佐证"（有没有外部证据）无法自动判断，只能查"修法"是否存在。**其余四步需要人工看。**

---

## 已知的假阳性

- **R4**：有些段落的反例是"换成另一种写法会怎样"，既不是"删"也不是"写歪"，会被判成单侧。这是设计取舍——宁可多提醒一次。
- **R5**：如果一句话恰好以"比喻"开头但不是在给手法命名，会被误判。目前没有上下文判断。

---

## 与模板的关系

- `_解析模板（从猫猫庙第二版提炼）.txt` —— 给人看的范例
- `tools/meow_lint.py` —— 给机器判的规则

**两者必须同步改**：模板里加了新要求，规则里就要加一条检查，否则模板会慢慢变成一句口号。
