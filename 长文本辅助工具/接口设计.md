# 接口设计 · 长文本辅助工具插件

> 目标：把现有的一堆脚本，变成**可以被调用的工具**。
> 调用者是 AI（我），不是人。人只负责写稿。

---

## 零、一条架构原则

> **算归代码，判归模型，骂归模型。**

| 什么 | 谁做 | 为什么 |
|---|---|---|
| 指标计算（落差、节奏、熵） | **代码** | 模型算不准，且必须可复现 |
| 判断（强度 0-3、六条判据、笑点） | **模型** | 代码判不了语义 |
| 分数汇总、证据核对 | **代码** | 数字必须对得上 |
| 嘲讽文案 | **模型** | 模板只能给骨架 |

**代码负责不撒谎，模型负责不敷衍。**

## 一、五个工具

### 1. `lt_annotate` —— 拿标注骨架

模型要标什么，工具先把格子摆好。

```json
输入：
{
  "text": "正文全文",
  "mode": "paragraph"        // 按段切
}

输出：
{
  "total_chars": 1330,
  "paragraphs": [
    {"para": 1, "text": "猫猫山上猫猫庙……", "need": ["strength","direction","function","open_q","dtype"]}
  ],
  "schema_version": "1.0"
}
```

**为什么不让模型自己切段**：切段要一致，否则两次评分对不上。

---

### 2. `lt_score` —— 算分

模型把标注交回来，代码算指标和分数。

```json
输入：
{
  "text": "正文全文",
  "annotations": [ {P1 标注} ],
  "theme": { 暗线补充窗口 },
  "citations": [ {引用} ],
  "options": {"zigzag_threshold": 2}
}

输出：
{
  "total": 83.83,
  "max_possible": 100,
  "unmeasured": [{"item":"视角衔接","points":2,"reason":"指标不可靠"}],
  "sections": [
    {"id":"atmosphere","name":"氛围铺垫","score":35.58,"full":40,
     "items":[{"id":"drop","name":"氛围波动落差","score":6.88,"full":7.5,
               "evidence":"最大落差 5 级 / ≥4 级 6 个"}]}
  ],
  "evidence": [
    {"type":"logic_missing","para":4,"detail":"「小伙伴们」首现段4、末现段6，之后再无交代"},
    {"type":"self_scored","item":"暗线","points":10.25}
  ],
  "warnings": ["暗线为作者自评，非工具判定"]
}
```

**`evidence` 是核心字段。** 嘲讽必须从这里面取材料，
**不许模型自己编证据。**

---

### 3. `lt_taunt` —— 取嘲讽素材

分数出来，取对应的语气档 + 可用模板 + 证据。

```json
输入：{"score": 83.83, "evidence": [...], "style": "auto"}

输出：
{
  "band": "80-90",
  "force": "普通嘲讽",
  "styles": ["雌小鬼","绿茶","钱钟书式"],
  "templates": [
    {"id":"t-012","style":"雌小鬼","mechanism":"借第三方的刀",
     "tpl":"{score} 呀～不过人家算了一下，这里面有 {self} 分是你自己填的呢。",
     "slots":{"score":"83.83","self":"10.25"}}
  ],
  "rules": ["每句必须挂 evidence","95 分以下不给鼓励","一条最多两个比喻"]
}

然后模型拿模板**改写**，不照抄。
```

---

### 4. `lt_plan` —— 创作模式：排曲线

写之前先排。

```json
输入：{"genre":"抒情散文","length":1400,"arc":"先扬后抑"}

输出：
{
  "plan": [
    {"para_range":[1,6],"function":"安抚","target_strength":1,"note":"定调"},
    {"para_range":[7,19],"function":"蓄势","target_strength":2,"note":"必须让主角在场"}
  ],
  "warnings":["这段 13 段同类，容易单一视角"]
}
```

**创作模式不打分。** 只在写完后用 `lt_score`。

---

### 5. `lt_read` —— 阅读模式：给地图

给人或给 AI 读长文之前先看地图。

```json
输入：{"text":"长文"}

输出：
{
  "map":[{"para":1,"function":"安抚","strength":1,"open_q":"—"}],
  "curve":{"peaks":[19,25,30],"valleys":[3,22,28]},
  "foreshadow":[{"para":9,"q":"鼠球是什么","resolved_at":19}],
  "advice":"第 3-19 段是长爬坡（16 段），此处别跳读"
}
```

## 二、数据结构（三种，都是 JSON）

### Annotation（P1 标注，一段一条）

```json
{
  "para": 7,
  "strength": 1,
  "direction": 1,
  "function": "铺垫",
  "open_q": "—",
  "dtype": "角色",
  "q_resolved": null,
  "unplanted": [],
  "logic": [],
  "carrier": null,
  "citations": []
}
```

字段规则：
- `strength` 0–3 整数
- `direction` -1 / 0 / 1
- `function` 只能是：交代/铺垫/蓄势/释放/转折/回收/安抚/留白
- `dtype` 只能是：角色/环境/心理/事件/其他
- **凡工具判不了的，字段留 `null`，由模型填**

### Theme（暗线补充窗口）

```json
{
  "statement": "一句话说清暗线",
  "anchors": [
    {"name":"小山","under":"承载童年的容器",
     "states":[{"para":3,"state":"磕碜","keys":["磕碜"],"dir":-1}]}
  ],
  "scores": {"1":1.0,"2":1.0,"3":0.75,"4":3.0,"5":3.0,"6":1.5}
}
```

### Report（最终报告）

见 `lt_score` 输出。**这是唯一给外面看的结构。**

## 三、错误处理（三条硬规则）

**1. 字段缺失 = 拒绝算，不猜。**
```
{"error":"missing_annotation","detail":"段 7-19 缺 strength","recoverable":true}
```
不拿默认值填充。缺就是缺。

**2. 不可测的项，明说不可测。**
`unmeasured` 数组必须列出。宁可少给 2 分，不给假分。

**3. 自评项必须打标。**
凡是作者自己填的分，`warnings` 里写明。
**读者有权知道哪个分不是算出来的。**

---

## 四、为什么不做成"一键出分"

因为一键出分必然要模型替作者判断，
而判断一旦被模型代劳，作者就不会再想自己的稿子。

**流程必须留出人（或模型）动手的环节：**

```
lt_annotate  → 模型标注 → lt_score → 模型写嘲讽
     ↑                        ↓
   人能改                  证据可查
```

**这不是麻烦，这是设计。**

## 五、与 DSH 的接法（实现层面）

现有脚本已经在 `长文本辅助工具/` 下：

```
p1_curve.py     曲线与峰谷
p2_score.py     氛围铺垫五项
p3_score.py     伏笔台账
p5_score.py     描写叙述

p7_logic.py     逻辑

p9_link.py      衔接
p10_joke.py     笑料

```

**打包成一个 MCP server**（`lt-tools.mjs` 或 python），暴露上面五个工具。
参数是 JSON，返回也是 JSON。

**注意**：MCP 工具的参数名不要和内部函数名撞（踩过 `text` 遮蔽的坑）。

## 六、版本与兼容

```
schema_version: 1.0
```

规则变了就升版本号。**旧标注必须能读**——
因为作者会用 1.0 标完一篇文章，不能因为工具升级就作废。

升级时：新字段设默认值（`null`），旧字段不删。

## 七、还没定的

1. **模型标注的稳定性**：同一篇标两次，分数会不会差 3 分以上？
   这是"能不能叫量化"的唯一检验，还没验过。
2. **多篇对比**：现在只能单篇。跨篇比较需要标准化。
3. **梗库联网更新**：接口留了 `citations`，但"过时"判断还没接热点数据。

## 九、第六个工具：`lt_feedback`

报告末尾必须带反馈区块，否则这个工具永远只是我在猜。

```json
输入：
{
  "report_id": "rpt-20261105-0001",
  "verdict": "partial",           // agree / partial / disagree
  "taunt_reaction": "broken",     // broken / stung / flat / wrong
  "skeleton": "骨 3",             // 这次用的是哪条骨架
  "disputes": [
    {"section":"logic","item":"小伙伴消失","tool_score":7.5,"user_score":9.0}
  ],
  "quoted_dispute": "这句我不认：……"
}

输出：
{"ok": true, "feedback_id": "fb-0001"}
```

### 三条回路

```
反馈
 ├─→ 骨架胜率   broken+1 / stung+0.3 / flat 0 / wrong −1
 ├─→ 判据校准   同一项连续 3 次同向偏差 → 建议改阈值
 └─→ 事实错误   wrong → 立刻下架，不辩论
```

### 两条不能破的规矩

**一、反馈不能直接改分。**
用户说自己该 90 分，不能当场改成 90——那样工具就成了哄人器。
**分数必须由规则算，不能由情绪改。**

**二、骂得狠不改，骂错了必须改。**
`wrong` 是唯一会立刻下架嘲讽的理由。
**狠是风格，错是硬伤。**
