## 四、实施顺序（四步）

### 第 1 步 · 把 p*.py 收进 `rules/`，统一接口

现在每个 p 都是 `main()` 打印，要改成**函数返回 dict**：

```python
# 现在
python p2_score.py 标注.jsonl   # 打印一堆

# 之后
from rules.atmosphere import score
result = score(annotations)      # 返回 dict
```

**这一步不做，插件永远只能靠 subprocess 抓输出。**

### 第 2 步 · 定 schema，出报告结构

按 `接口设计.md` 的 `Report` 结构，把所有规则的输出拼成一个。

**验收**：猫猫庙跑出来的总分，和现在手算的 83.83 一致。

### 第 3 步 · 包成 MCP server

`server.mjs` 注册六个工具，参数走 JSON。

**踩过的坑（必须避开）：**

| 坑 | 规避 |
|---|---|
| MCP 参数名叫 `text` 会遮蔽内部函数 | 参数一律加后缀（`text: body`） |
| `cordis.patch.yml` 每次重启被重写 | 加入 `setup-dsh.mjs` 的 `MANAGED_MCP_IDS` |
| 会话工具列表是创建时快照 | 装完必须 `session/reset` |
| 工具插件改 `.mjs` 要重启 DSH | 改前先备份 |

### 第 4 步 · 补完缺口

| 缺什么 | 影响 |
|---|---|
| 衔接的视角 2 分 | 总分上限只有 98 |
| 笑料的"梗库联网更新" | 梗过时判断靠人 |
| 多篇对比 | 现在只能单篇 |

## 五、验收标准（先定，免得到时候自我感觉良好）

**插件做成了，必须同时满足：**

1. **一条命令跑完全流程**，不需要人在中间手动传文件
2. **总分和手算一致**（猫猫庙 83.83 / 100）
3. **同一个标注跑两次，分数差 ≤3 分**
4. **报告里每条扣分都带段号和句子**
5. **反馈能写进 `反馈记录.txt` 并回流到骨架胜率**

**第 3 条是最硬的**——它不过，前面全是假量化。

## 六、不该放进插件的东西

| 东西 | 为什么不放 |
|---|---|
| P1 标注本身 | 那是判断，必须模型/人做，不能写死在插件里 |
| 嘲讽句子 | 生成的不入库，用完就丢 |
| 具体文章 | 插件是工具，不是数据库 |

**插件只装"规则"和"数据"，不装"作品"和"判断"。**

---

## 七、一个提醒

从散装脚本到插件，**最容易出问题的不是代码，是接口**。

因为代码错了会报错，**接口错了会静默地算错**——
比如单位不一致（级 vs 分）、字段名不一致（segs vs segments），
跑起来没报错，分数就是错的。

**所以第 2 步（定 schema）不能跳，也不能边走边改。**
