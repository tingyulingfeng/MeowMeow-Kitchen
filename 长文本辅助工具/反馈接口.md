# 反馈接口 · 报告末尾的回路

> 每次评审结束时，报告最后给出一段「反馈」区块。
> **反馈不是收集意见，是校准工具。**

---

## 一、报告末尾长什么样

```
────────────── 用户反馈 ──────────────

这次评审，你觉得：
  ① 分数服不服？      [ 服 / 部分不服 / 完全不服 ]
  ② 嘲讽准不准？      [ 破防 / 只是难受 / 无感 / 说错了 ]
  ③ 哪一项分不认？     可多选（见下方分项）
  ④ 有没有一句让你想反驳？  贴出来，我记下来

────────────── 反馈编号 ──────────────
report_id: rpt-20261105-0001
```

---

## 二、反馈的数据结构

```json
{
  "feedback_id": "fb-0001",
  "report_id": "rpt-20261105-0001",
  "submitted_at": "2026-11-05T01:40:00+08:00",

  "verdict": "partial",           // agree / partial / disagree
  "taunt_reaction": "stung",      // broken(破防) / stung(难受) / flat(无感) / wrong(说错了)

  "disputes": [
    {
      "section": "logic",
      "item": "小伙伴们中途消失",
      "tool_score": 7.5,
      "user_score": 9.0,
      "reason": "我就是要他们消失，故意的"
    }
  ],

  "quoted_dispute": "这句我不认：……",
  "free_comment": ""
}
```

---

## 三、三个选项字段的含义

### `verdict` —— 分数服不服

| 值 | 含义 | 触发什么 |
|---|---|---|
| `agree` | 服 | 不改 |
| `partial` | 部分不服 | 记入争议清单，等第二次反馈确认 |
| `disagree` | 完全不服 | **标记该篇为待复核**，不直接改分 |

### `taunt_reaction` —— 嘲讽准不准

| 值 | 含义 | 触发什么 |
|---|---|---|
| `broken` | 破防 | **这条骨架记 +1 分** |
| `stung` | 只是难受 | 记 0 分（有效但不够狠） |
| `flat` | 无感 | **这条骨架记 −1 分** |
| `wrong` | 说错了 | **立刻下架该条，并标记为"事实错误"** |

**`wrong` 是唯一会直接下架的理由。** 骂得狠不算错，骂错了才算。

### `disputes` —— 哪一项分不认

这才是最值钱的部分。它能校准判据：

- 同一条判据被 **3 次以上**判"偏高/偏低" → 重新校准阈值
- 只是单次不服 → 先记着，不动

---

## 四、反馈怎么回流（三条回路）

```
反馈
 ├─→ 嘲讽库    taunt_reaction 决定骨架的胜率（骨 9 破防 3 次 / 无感 5 次 → 降权）
 ├─→ 判据校准  disputes 连续 3 次同向 → 调阈值或改判据
 └─→ 事实错误  wrong → 立刻下架，不辩论
```

### 回路一：骨架胜率

每条骨架记两个数：

```json
{"skeleton": "骨 3", "broken": 3, "stung": 2, "flat": 5, "wrong": 0}
```

**胜率 = (broken × 1.0 + stung × 0.3) / 总次数**

胜率低于 0.2 的骨架，标记 `suspect`，优先换掉。

### 回路二：判据校准

```json
{"rule": "logic", "direction": "user_higher", "count": 3,
 "avg_delta": 1.5, "note": "用户三次都说逻辑扣重了"}
```

连续三次同向 → 我在报告里提示改判据，**改不改由作者定**。

### 回路三：事实错误

`taunt_reaction: "wrong"` 的，**不看理由，先下架**。
再问一句"哪里错了"，记进 `wrong_note`。

**骂狠了不改，骂错了必须改。** 这条界线不能糊。

## 五、作者那边的"接收端"

作者需要建的东西：

| 要什么 | 最小实现 |
|---|---|
| 一个能提交反馈的入口 | 一个 txt 文件/一个表单/一个 QQ 消息都行 |
| 每条反馈带 `report_id` | 报告末尾自动生成 |
| 能按月导出 | `反馈表.jsonl` 就是导出格式 |

**不需要数据库，不需要服务器。**
一个人用的工具，`jsonl` 追加就够了。

---

## 六、为什么反馈必须结构化

如果只收"我觉得你说得不对"，那就什么也改不了。

**必须落到具体项：**
- 哪一项（section + item）
- 工具给几分、你认为该几分
- 为什么

**这样三次之后，工具就知道自己哪里虚高、哪里虚低。**

---

## 七、一个自我约束

**反馈不能直接改分。**

用户说自己该 90 分，不能当场改成 90——
那样工具就变成了"哄人器"。

反馈只能做两件事：
1. **校准判据**（长期、多次、同向）
2. **淘汰无效嘲讽**（骨架胜率）

**分数必须由规则算，不能由情绪改。**

---

## 八、用户侧：五个空，一个文件（2026-11-05 定稿）

作者原话：**用户侧提交反馈，我这边接收并按时间顺序记录到文本，先这样。**

那就越简单越好。用户拿到报告后，只需要填这个文件：

```
report_id:
服不服:
嘲讽准不准:
哪项分不认:
想反驳的一句:
想说的话:
```

`report_id` 从报告末尾抄，其余四行按提示填。

### 填完交给接收端

```bash
python lt_feedback.py intake 用户填好的.txt
```

**会同时写两个地方：**

| 文件 | 干什么用 |
|---|---|
| `反馈记录.txt` | **按时间顺序，人能直接读**，只追加不改 |
| `反馈表.jsonl` | 结构化，用来算骨架胜率和判据偏差 |

### `反馈记录.txt` 长这样

```
反馈记录（按时间顺序，只追加）
========================================================

[2026-11-05T01:19:09]  fb-0001  ←  rpt-20261105-0001
  分数态度：部分不服
  嘲讽反应：难受
  不认的项：逻辑那一项，我觉得扣重了
  想反驳：「你把小伙伴砌进墙里了」——我没有，我是故意的
  想说的：别的都还行
```

**这个文件给作者看，不需要懂 JSON。**

### 容错

用户填错也没关系：

- `服不服` 只认「服 / 部分不服 / 完全不服」，填别的会被拒绝并告诉他该填什么
- `嘲讽准不准` 只认「破防 / 只是难受 / 无感 / 说错了」

**宁可当场退回去让他重填，也不要收进来一条看不懂的记录。**

分项争议还在文本里，没做结构化。
等攒够十几条，再统一录成 `disputes` 数组。

**先跑起来，比先设计完美重要。**
